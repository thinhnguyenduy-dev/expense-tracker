1 Kiến trúc tổng quan

ReAct Agent hoạt động thế nào

App dùng kiến trúc một ReAct Agent duy nhất (dựng bằng create_react_agent): một agent sở hữu toàn bộ tool, tự suy luận và quyết định gọi tool nào, chạy tool, đọc kết quả, rồi lặp lại cho đến khi đủ thông tin để trả lời..

1
Agent nhận requestLLM đọc history + system prompt (đã nhúng ngày, categories, tiền tệ, user_id), quyết định: trả lời thẳng hay gọi tool.
2
Gọi tool (nếu cần)Node tools thực thi các tool_calls, ghi ToolMessage vào State rồi quay lại agent.
3
Lặp ReActAgent đọc kết quả tool → gọi tool tiếp hay trả lời. Vd: duckduckgo_search → tính tổng → submit_expense_tool — nhiều bước trong CÙNG một lượt.
4
Kết thúcKhi agent trả lời bằng text (không còn tool call) → END. An toàn nằm ở chính các tool (SQL read-only, user-scoping) và system prompt.

2 Chi tiết 2 Nodes

create_react_agent sinh ra một graph cực gọn chỉ gồm 2 node: agent (LLM) và tools (ToolNode). Toàn bộ logic "làm gì tiếp theo" do chính LLM quyết định qua tool calling — agent xuất tool_calls để dùng tool, hoặc trả lời để kết thúc.

🧠 agent Entry Point

LLM được bind toàn bộ tool (giao dịch + đọc + SQL read-only + web search). Mỗi lượt nó đọc history + system prompt (đã nhúng ngày, categories, tiền tệ, user_id) rồi xuất hoặc tool_calls (cần dùng tool) hoặc câu trả lời cuối. An toàn (từ chối phá hoại / lộ .env) đến từ system prompt + giới hạn của tool.

có tool_calls → tools
không còn tool call (trả lời text) → END
🔧 tools
ToolNode

LangGraph's ToolNode — nhìn AIMessage.tool_calls, thực thi tool, ghi ToolMessage vào State, rồi luôn quay về agent để LLM đọc kết quả và quyết bước kế (đây chính là vòng ReAct). Đặc biệt: nếu một tool gọi interrupt() (ngoại tệ trong submit_expense_tool, hoặc ask_clarification_tool), graph tạm dừng ngay tại đây chờ Command(resume) (xem Section 6).

4 Checkpoint – Bộ nhớ dài hạn của Agent

Khi gọi AsyncPostgresSaver(pool), LangGraph tự tạo 4 bảng trong PostgreSQL — không cần viết migration thủ công. Nhờ đây, agent nhớ lịch sử hội thoại giữa các request và có thể resume sau crash.

📸 checkpoints Core

Snapshot toàn bộ State sau mỗi node. Mỗi row = 1 bước, liên kết thành chuỗi lịch sử qua parent_id.

  • thread_idID cuộc hội thoại (UUID)

  • parent_checkpoint_idTrỏ về bước trước → chuỗi lịch sử

  • metadatastep#, source, user_id, currency
🗜️ checkpoint_blobs Storage

Data lớn lưu tách riêng dưới dạng binary nén. Tránh bảng checkpoints quá nặng khi messages dài.

  • thread_idKhóa liên kết

Ghi trung gian khi node đang chạy. Nếu server crash, LangGraph đọc bảng này để resume chính xác.

6 Human-in-the-Loop (HITL)

Có lúc agent cần hỏi lại user giữa chừng rồi mới làm tiếp — ví dụ chi tiêu bằng ngoại tệ thì phải biết tỷ giá. LangGraph cho việc này bằng cặp primitive interrupt() & Command(resume=...): interrupt() tạm dừng graph ngay tại chỗ đang chạy và ghi state xuống checkpointer; lượt sau gọi Command(resume=<đáp án>) thì graph chạy tiếp đúng điểm dừng, không khởi động lại từ đầu.

⚠️ "Tạm dừng" = state bền trong DB, KHÔNG phải process sống

Mỗi request mở pool → ainvoke() → gặp interrupt() là return ngay, pool đóng, hàm kết thúc sạch. Điểm dừng được ghi vào Postgres chứ không có coroutine/thread nào bị giữ trong RAM. Nhờ vậy 10.000 hội thoại "đang chờ tỷ giá" vẫn tốn 0% CPU — chúng chỉ là vài dòng checkpoint.

Hai đường kích hoạt interrupt

# ai.py – resume an toàn
if is_resume:
    snapshot = await graph.aget_state(config)
    resume_pending = bool(snapshot.interrupts)

input_state = (
    Command(resume=message) if resume_pending
    else {"messages": [HumanMessage(message)]}
)
final_state = await graph.ainvoke(input_state, config)

if final_state.get("__interrupt__"):       # đang treo chờ user
    q = final_state["__interrupt__"][0].value["question"]
    return {"needs_clarification": True, "response": q}

Khi user bỏ ngang — dọn thread treo

Bỏ ngang không rò rỉ process (pause chỉ là state bền), nhưng để lại checkpoint rác trong DB và có thể "lệch pha": user quay lại gõ tin mới khi thread vẫn còn interrupt treo. Hai biện pháp:

  • Vá lỗ hổng lệch pha: luôn check snapshot.interrupts; nếu treo mà user gửi tin mới (is_resume=false) → coi như hủy, gọi checkpointer.adelete_thread(thread_id) rồi bắt đầu lượt mới.
  • Job quét định kỳ: dùng AsyncIOScheduler sẵn có (main.py) thêm job 24h gọi adelete_thread() cho các thread treo quá hạn — khớp pattern recurring/reminder job hiện tại.
